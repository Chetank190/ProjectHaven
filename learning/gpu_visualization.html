Haven Matrix — GPU & ML Architecture

How the models run on the GPU, and an honest account of where the accelerator is mandatory, where it's strongly justified, and where it's a pattern built to scale. A dual-gateway social-services triage system.

01Three workloads, one device

Haven Matrix runs three independent ML workloads on a single GX10. They differ sharply in how much they actually need a GPU — and we say so plainly.

🧠

LLM Triage

Nemotron-30B / Gemma 3n E4B

Caseworker notes & kiosk speech → strict NeedsPayload JSON. Deterministic compiler (temp 0), not a decision-maker.

● GPU mandatory
🎙️

Speech Recognition

Parakeet-1.1B-TDT (NIM)

Kiosk voice → transcript, on-device. Audio never leaves the box when the local NIM is up — a hard privacy boundary.

● GPU strongly justified
📍

Geospatial Solve

cuML KNN + cuDF (haversine)

Constraint-masked nearest-eligible-service search. Correct & GPU-native today; the real payoff arrives at city→country scale.

● GPU = scaling story

04The honest part: where GPU doesn't yet pay off

Measured solve times are ~12–135 ms (from daily_telemetry.csv). At today's data scale — hundreds of shelters, ~1,600 rows in the largest pillar — the KNN math is microseconds; the rest is Python/cuDF overhead.

Relative solve cost — illustrative, by data scale

Verdict for judges: The LLM and ASR are the load-bearing GPU justification — a 30B model and real-time STT are simply not CPU problems. The cuML solver is an honest demonstration of a GPU-native data pattern that is correct and ready for scale, deployed today on small data for free because the accelerator is already hot for the model.

06One-line justifications

The mandateA 30B local LLM and real-time ASR are not CPU problems.
The memory128 GB unified lets the model and the city's data share one address space, zero-copy, offline.
The scaleThe solver is GPU-native, so it grows from one city to a country with no rewrite.
The resilienceEverything has a CPU fallback. The GPU makes it fast; it doesn't make it fragile.
